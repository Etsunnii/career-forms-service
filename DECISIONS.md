# Решения для MVP и пересдачи

Это описание фактической реализации. Записи подготовлены при работе с AI; они не заменяют самостоятельную проверку и понимание кода кандидатом.

## Локальный JSON вместо отдельной базы

ТЗ разрешает JSON или SQLite. Для небольшого однопроцессного MVP JSON сокращает настройку: после двух команд запуска уже можно работать. SQLite лучше подходит для большого числа записей и выборок, но здесь не требуется для выполнения основного сценария.

Все изменения проходят через очередь. Каждая запись создаёт новое состояние и временный файл; только после успешного переименования меняется состояние в памяти. При ошибке на диске ранее сохранённые данные остаются. Реальный отказ записи и последующее восстановление очереди проверены тестом.

Ограничение: весь файл читается и переписывается целиком, а процесс должен быть один. При росте данных нужны SQLite, выборки и пагинация. Заявления о работе нескольких процессов или полной устойчивости к потере питания для этой реализации нет.

## Сохранение редактора

Во время запроса поля блокируются и кнопка показывает ожидание. Альтернатива — разрешить продолжать ввод и отдельно учитывать новые правки. Для MVP блокировка проще для понимания. Счётчик локальных изменений дополнительно защищает от позднего ответа: если состояние всё же изменилось, новые правки остаются несохранёнными.

Неуспешный запрос не стирает текст. Проверено задержкой запроса, отказом сети и повторной попыткой.

## Две независимые версии

`draftVersion` защищает редактор. Каждое сохранение передаёт номер загруженного черновика. Сервер сравнивает номер внутри очереди записи. При конфликте возвращает 409 и не меняет данные. Клиент оставляет правки на экране, позволяет открыть свежую версию и скачать свои изменения. Автоматическое слияние разных наборов вопросов не реализовано, чтобы избежать неоднозначных результатов.

`revision` описывает публичные вопросы. Она увеличивается при изменении полей и правил ответов. Название, описание и повторная публикация той же схемы не меняют `revision`. Последняя опубликованная схема сохраняется также после закрытия приёма. Поэтому повторное открытие неизменённой формы не создаёт лишнего конфликта.

Сохранение и публикация — два HTTP-запроса. Публикация тоже проверяет `draftVersion`: если другая вкладка успела изменить черновик между запросами, чужой вариант не публикуется молча.

## Один отклик в рамках сессии

Выбрано правило: один принятый отклик на форму в одной сессии вкладки. Это простая защита от случайных дублей, без обещания определить уникального человека.

Если запрос с теми же нормализованными ответами и версией пришёл повторно, сервер возвращает прежний идентификатор и HTTP 200. Первая запись возвращает HTTP 201. Если ответы отличаются, сервер возвращает 409 `ALREADY_SUBMITTED` и прямо сообщает, что новые ответы не сохранены. После обновления страницы показывается состояние «уже отправлено».

Рассмотренный вариант: разрешать несколько откликов из одной сессии и выдавать отдельный ключ каждой новой попытке. Для этого потребуется явное действие «Отправить новый отклик» и отдельная политика повторов. Оно не нужно выбранному MVP.

## Обновление формы во время заполнения

При реальном изменении вопросов старую версию нельзя молча проверить по новым правилам: мог появиться обязательный вопрос или исчезнуть вариант. Поэтому сервер возвращает 409 `FORM_CHANGED`. Студент может обновить форму одной кнопкой, после чего восстановятся ответы на оставшиеся поля. Он должен проверить обновлённые вопросы перед отправкой.

Незавершённые ответы лежат только в `sessionStorage` данной сессии. После успешной отправки локальный черновик удаляется. При запрете браузерного хранилища само заполнение работает; восстановление после перезагрузки не обещается. Проверены оба случая.

## Проверяемость

Серверные тесты покрывают данные, версии, параллельность и перезапуск. DOM-тесты используют настоящие обработчики приложения и временный HTTP-сервер. Они проверяют нажатия и содержимое полей, но не заменяют реальный браузер для визуальной проверки.

При ручной проверке следует записать браузер, версию Node.js и фактический результат. Зелёные автоматические тесты не подтверждают визуальную проверку в настоящем браузере.
